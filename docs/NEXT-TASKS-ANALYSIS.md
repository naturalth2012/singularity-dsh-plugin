# 后续任务执行顺序分析

> 分析时间：2026-11-27 | 方法：实证测量，不凭直觉排序
> 结论先行：**v2.2 数据串 → 反馈回路立项 → Playwright（条件不成熟，暂缓）**

## 1. 三个候选的真实约束（实测）

### 候选 A：v2.2 calibration 数据串 i18n（10 条）

| 维度 | 实测 |
|---|---|
| 数量 | 10 条（6 条 caveat/reason + 4 条 why） |
| 跨越层数 | **3 层**：`calibrate.cjs` → `calibration.json` → `inject-calibration.cjs` → `client.js` |
| 引擎影响 | **零** |
| 断言影响 | 零（现有断言查的是中文，翻译后仍可查 key） |
| 渲染风险 | **零**（数据串是纯文本，不参与结构） |
| 工作量 | 中（要改构建链路 + 双语字段设计） |
| 可回滚性 | 高（独立提交） |

**关键难点**：数据串在 JSON 里是**单一字符串**，双语化需要设计成
`{ zh: "...", en: "..." }` 结构，或拆成 `caveatZh` / `caveatEn` 两个字段。
后者更简单，但会让 calibration.json 结构变化，需同步改 inject 脚本与 client 读取。

### 候选 B：反馈回路（原 T7）

| 维度 | 实测 |
|---|---|
| `derive` 函数 | 2427 字符，**已接收 `prev` 参数** |
| `prev` 使用 | 仅 2 处（`prev`、`prev.gross`）——前馈痕迹很浅 |
| 现有断言总数 | **355 条** |
| 硬编码基线断言 | `算力封建制`×15、`66.1`、`22.8`、`46.1`、`0.59`×3 |
| 引擎影响 | **会重写 `derive`，全部基线可能移动** |
| 六剧本基线 | 全部 6 个剧本的结局/租金/渗透都会变 |
| 校准数据 | 全部 11 个字段都要重算 |
| 文档影响 | MODEL-CONTRACT §1–§9、README、DETAIL 都要改 |

**关键判断**：这是**唯一会移动基线的改动**。一旦引入反馈回路，
六剧本结局可能从「算力封建制」变成别的，355 条断言里至少 25 条要重新标定，
校准报告全部重算，契约 §9 的 10 条局限要重写。

**这不是「加个功能」，是「换一个模型」。** 按既有流程，它需要：
需求细分 → 需求审核 → 校准（大样本验证新动力学） → 详细方案 →
方案审核 → 分批执行 → 验证 → 交付。**是一个独立版本周期，不是一次增量。**

### 候选 C：Playwright 视觉/交互回归

| 维度 | 实测 |
|---|---|
| Playwright | **未安装** |
| Puppeteer | **未安装** |

## 2. 依赖关系图

```
v2.2 数据串 i18n ──→ 独立，零依赖，零风险
                        │
反馈回路（T7）──────────┘ 会移动基线 → 必须在 i18n 全部完成后做
                        │     （否则翻译又要跟着基线重做一遍）
                        ↓
Playwright ─────────── 依赖：① 安装 Playwright ② 解决 GUI 401
                              两者都不具备 → 阻塞
```

**关键依赖**：反馈回路会移动基线，而基线里的结局名/阶段名是**中文**
（不翻译的引擎语义）。所以 i18n 和反馈回路**不冲突**——
i18n 翻的是视图层，基线动的是引擎值。

但反过来：如果先做反馈回路，校准数据全部重算，
v2.2 的双语数据串设计就要跟着改一遍。**先 i18n 后反馈回路更省。**

## 3. 建议顺序（含理由）

| 顺序 | 任务 | 理由 | 预计规模 |
|---|---|---|---|
| **第 1** | **v2.2 数据串 i18n** | 零引擎风险、零断言影响、可独立回滚；且它改的是 calibration 结构，**必须在反馈回路重算校准之前完成**，否则要做两遍 | 小-中 |
| **第 2** | **反馈回路立项（v3.0）** | 唯一会移动基线的改动，需完整八步流程。必须先出**立项文档**说清：新动力学是什么、六剧本会怎么变、355 条断言怎么迁移、契约 §9 怎么重写 | 大（独立周期） |
| **第 3** | Playwright | **前置条件不成立**：未安装 + GUI 401 无 token。需要你先提供 GUI 访问方式，否则不做 | 阻塞 |

## 4. 第 1 项的具体方案要点

**不采用** `{ zh, en }` 嵌套对象（会让 client 读取变复杂），
**采用**平行字段：

```json
"caveat": "中文原文",
"caveatEn": "English text"
```

理由：
- `client.js` 读取时只需 `isEn ? d.caveatEn : d.caveat`
- `inject-calibration.cjs` 的 slim 映射只需多带一个字段
- 现有断言（查中文）不受影响
- 向后兼容：没有 `caveatEn` 时回退到 `caveat`

**受影响的 10 条**（分布在 `stageReachability` 与 `asymmetries`）：
1. `collapseGain.caveat`（该系数是编译期常量…）
2. `socialDemocracy.caveat`（reformRoom 折减…）
3. `chattering.caveat`（前馈模型无内生临界点…）
4. `stageReachability.structurallyUnreachable[0].reason`（stageOf 最低只返回…）
5. `stageReachability.rareButReachable[0].note`（需同时满足 pen≥0.68…）
6. `stageReachability.start2024.caveat`（2024 年 u=0…）
7. `stageReachability.techOnlyBeforeGate.caveat`（pen < GATE_PEN 时…）
8-10. `note`、`anchors[].name` 相关（需确认）

## 5. 第 2 项的立项必须先回答的问题

反馈回路不是「加个 prev 依赖」那么简单。立项文档必须回答：

1. **反馈的是什么？** 选项：不平等 → 制度变迁；租金 → 政治捕获；崩解 → 技术倒退。
   每种都会产生不同的新稳态，不能随便选。
2. **六剧本会变成什么？** 必须先用大样本验证新动力学的稳定性，
   否则可能引入路径抖动（现有断言「翻转 ≥6 次的样本为 0」会失败）。
3. **契约 §9 的 10 条局限怎么办？** 反馈回路恰好解决 §9.4「前馈而非动力学」，
   但可能引入新的局限（如多重均衡、初值敏感）。
4. **355 条断言怎么迁移？** 是全部重新标定，还是保留旧基线作「v2.x 兼容模式」？
   后者更安全但要维护两套模型。

**我的建议**：反馈回路应做成**可选动力学模式**（`dynamics: 'feedforward' | 'feedback'`），
默认保持 feedforward，这样：
- 现有基线不变 → 355 条断言全部保留
- 新动力学作为实验特性，独立验证
- 用户可对比两种模式的差异（这本身就是好功能）

## 6. 不做的事

- 不跳过立项直接改引擎（会毁掉 355 条断言的可信度）
- 不在前置条件不成立时硬上 Playwright
- 不为了「有事可做」而选低价值任务
