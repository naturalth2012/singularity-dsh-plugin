## 5. 发现的问题：校准元信息滞后（已修）

**现象**：`docs/calibration.json` 的 `version` 字段停在 `1.8.0`，
`commit` 停在 `5534922`（v1.7.0），而插件已是 2.0.0。v1.9 与 v2.0 都未重新生成。

**判断**：不是数据错误，是元信息陈旧。但会让「模型体检」页显示错误的版本号，
属于诚实性问题。

**实证**：重新运行 `calibrate.cjs` 后逐字段对比——

```
实质差异（排除 generatedAt/version/commit）: 0 ✅
```

数据完全一致，证明引擎确实未变。已重新生成并注入。

**根因**：`calibrate` 脚本没有在发布流程里强制运行。v1.8 之后没有引擎改动，
所以没人注意到版本号没更新。

**修复**：本次已重算 + 重注入。建议后续在 `npm run verify` 前增加
「calibration.version === package.version」断言（见 §7）。

## 6. 排除的误报

审计过程中有三处疑似问题，逐一核实后确认是**审计脚本自身的缺陷**：

| 疑似问题 | 真相 |
|---|---|
| `T1`/`T2` 代码中找不到 | 与 `T0` 同行声明：`const T0 = 2024, T1 = 2050, T2 = 2060;` |
| `targetOf` 契约未提及 | 契约用 `simulate(target, ...)` 的 target 概念表达，非遗漏 |
| 分享/导出/导入函数不存在 | 实际名为 `shareLink` / `exportJson` / `importJson`，检查用了错名 |

**教训**：审计脚本的假阴性比代码缺陷更危险——它会让人误以为有问题而改坏代码。
每个「缺失」结论都必须用第二种方式复核。

## 7. 建议的后续加固

1. **校准版本断言**：`contract-check` 增加
   `calibration.version === package.json.version`，防止再次滞后。
2. **基线快照断言**：把六剧本基线值写进 `contract-check` 作为硬编码期望值，
   而不是仅靠「引擎区 hash 不变」间接保证。
3. **渲染片段数区间断言**：给七标签页的文本片段数设下界
   （如 health ≥ 110），防止「括号错位吞掉卡片」这类问题再次逃过语法检查。

第 3 条尤其重要——v1.8 开发过程中曾因括号错位导致 4 张卡被吞，
`node --check` 完全无法发现，是靠人工渲染探针才发现的。
